# LLM optimization #2 — merged analysis for vulnerability letters

## Изменение

Добавлен отдельный флаг:

```text
FSTEC_LLM_MERGED_VULN=1
```

Для vulnerability-писем вместо двух LLM-вызовов (`extract_iocs_llm` + `analyze`) теперь используется один merged-вызов `analyze_and_extract` на чанк. Остальные параметры LLM не менялись. Флаг выключен по умолчанию в коде, но включён в compose для стенда после проверки.

## Проверка

22 уникальных письма, полный прогон:

- До merged: **8 мин 31 с** (без dedupe).
- С merged: **4 мин 07 с**.
- Ускорение полного прогона: примерно **в 2 раза**.
- LLM active: mean **82.4 с**, median **90.6 с**, max **122.0 с** в merged-прогоне (по документам).
- Завершено: **22/22**, failed/зависших нет.

## Качество после изменения

| Поле | Результат |
|---|---:|
| BDU recall | 100% |
| BDU precision относительно эталона | 99.11% |
| CVSS версия | 99.55% |
| Severity | 97.29% |
| Применимость | 99.49% |
| Меры precision | 97.28% |
| Меры recall | 99.18% |
| Меры F1 | 98.21% |

Полевые метрики **не изменились** относительно предыдущего прогона. Ограничения по CVSS/severity связаны с актуальными данными BDU и ранее описанным расхождением с эталоном, а не с merged-режимом.

## Вывод

Merged-анализ vulnerability-писем:

- дал примерно **2x сокращение времени полного прогона на 22 уникальных письмах**;
- не ухудшил BDU/CVSS/applicability/меры в проверенном наборе;
- оставлен включённым на стенде.

## Следующий кандидат

Включить/проверить `FSTEC_LLM_MERGED_IOCS=1` отдельно, чтобы merged-вызов сразу возвращал IoC и не требовал fallback-вызова `extract_iocs_llm`. Это следующий независимый шаг.
