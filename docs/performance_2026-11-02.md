# Ускорение пайплайна — 2026-11-02

## Что изменено

### Очередь/concurrency

- LLM bus: 10 → 12, Kafka partitions: 12.
- LLM semaphore ограничен 12 (cap), вместо 16: GPU T4 уже загружен на 98%.
- Security: concurrency/bus 6 → 8.
- Reporting: bus 10 → 12.
- Ingest: bus 12 → 16, DB pool увеличен.
- DB pool: API/LLM/reporting до 24, security/ingest до 20.
- Kafka partitions оставлены 12: больше воркеров без repartition не даёт эффекта.

### GLPI/security

- Пер-документный prefetch уникальных продуктов GLPI вместо запроса на каждую уязвимость.
- Singleton GLPI-клиента на процесс + TTL-кэш `product → inventory` на 300 секунд.
- NVD и BDU для одной уязвимости запрашиваются параллельно.
- Prefetch BDU/NVD по всем ID письма, а не только при ≥3 BDU.
- Исправлена TLS-цепочка BDU: в security-контейнер проброшен CA-bundle хоста;
  это убрало повторные SSL-retry и таймауты.
- Поднят security concurrency до 8.

### Ingest/parse

- Ingest bus concurrency 16.
- Добавлен TTL-кэш результатов парсинга по SHA-256 содержимого (300 секунд, 128 записей).
- OCR/PDF-парсинг уже выполняется через `run_blocking`; event loop не блокируется.
- Отдельно увеличен DB pool ingest-сервиса.

## Пропускная способность

Короткие ramp-тесты, без часового прогона:

| Цель | Принято | Завершено | Acceptance | Completion |
|---|---:|---:|---:|---:|
| 360/ч | 24 | 24 | 350/ч | ~245/ч |
| 480/ч | 33 | 33 | 458/ч | ~286/ч |
| 720/ч | 45 | 45 | 660/ч | ~273/ч |

Вывод:

- GPU во время нагрузки **98%**, поэтому поднимать LLM concurrency выше 12 нельзя.
- Очередь LLM на 360/ч практически отсутствует; на 720/ч растёт, но все документы
  в тесте завершились.
- Подтверждённая максимальная устойчивая обработка — примерно **280–290 писем/час**.
- UI принимает до ~660–690 писем/час; ограничение находится в LLM, не в интерфейсе.

## Ограничения

- Полный часовой прогон не делался по требованию.
- Значения по cache/security зависят от температуры кэша.
- Этап LLM остаётся главным ограничением; следующий шаг — оптимизация LLM.
