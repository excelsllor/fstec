## 2. Схема подключения к внутренней БД инвентаризации (CMDB)

### 2.1 Требования подключения (ТЗ 4.3)
- Подключение — **только через API** (REST или SQL-коннектор), не напрямую к файлу БД.
- TLS 1.3, аутентификация Bearer/Basic (настройка в конфиге security-сервиса).
- CMDB недоступна в dev-контуре → используется **cmdb-mock** (тот же REST-контракт).

### 2.2 Контракт REST (рекомендованный)
```
GET {CMDB_ENDPOINT}/api/inventory/software?query=software&filter=version
```
Ответ:
```jsonc
{
  "items": [
    {"host": "srv-mail", "product": "OpenSSL", "vendor": "OpenSSL Project",
     "version": "1.1.1k", "cpe": "cpe:2.3:a:openssl:openssl:1.1.1k:*:*:*:*:*:*:*:*",
     "os": "RED OS 8", "last_seen": "2026-09-01"}
  ],
  "page": 1,
  "total": 2
}
```

### 2.3 Структура таблиц БД инвентаризации (проекция, согласуется с Заказчиком)

#### `inventory_servers` (хосты)
| Поле | Тип | Описание |
|---|---|---|
| `server_id` | INTEGER PK | Идентификатор хоста |
| `host_name` | VARCHAR(64) UNIQUE | FQDN/имя хоста |
| `os_name` | VARCHAR(64) | ОС (RED OS 8, Windows Server 2022…) |
| `os_version` | VARCHAR(32) | Версия ОС |
| `department_id` | INTEGER FK | Подразделение (опц.) |
| `last_seen` | TIMESTAMP | Дата последней инвентаризации |

#### `inventory_software` (установленное ПО)
| Поле | Тип | Описание |
|---|---|---|
| `sw_id` | INTEGER PK | Идентификатор записи |
| `server_id` | INTEGER FK → `inventory_servers` | Хост, на котором установлено |
| `product` | VARCHAR(128) | Название ПО (OpenSSL) |
| `vendor` | VARCHAR(128) | Производитель (OpenSSL Project) |
| `version` | VARCHAR(32) | Точная версия (1.1.1k) |
| `cpe` | VARCHAR(255) NULL | CPE-имя, если известно |
| `install_date` | DATE NULL | Дата установки/обновления |
| `last_seen` | TIMESTAMP | Дата последней инвентаризации |

#### `inventory_links` (связь ПО ↔ уязвимости, опциональная)
| Поле | Тип | Описание |
|---|---|---|
| `link_id` | INTEGER PK | Идентификатор связи |
| `sw_id` | INTEGER FK | ПО |
| `cve_id` | VARCHAR(20) NULL | CVE |
| `bdu_id` | VARCHAR(32) NULL | BDU:YYYY-XXXX |
| `patched` | BOOLEAN | Обновлено ли ПО |

### 2.4 Правила сопоставления (matching)
1. По `cpe` при наличии (строгое равенство/диапазон).
2. Иначе по `product` (нормализованное нижним регистром) + сравнение версий semver.
3. Если `current_version` попадает в уязвимый диапазон NVD/BDU → `Match=true`.
4. При Match → SLA «Критический», маршрутизация в отдел InfoSec, заметка `Обновить {Product} с {current_ver} до {fixed_ver}` (ТЗ 2.4).

## 3. Требования к аппаратному обеспечению

### 3.1 Состав (продуктивный сервер Заказчика)
| Компонент | Спецификация | Обоснование |
|---|---|---|
| ОС | RED OS 8.x amd64 + Docker (docker-compose) | Требование Заказчика |
| CPU | **16–24 ядра** (≥3.5 ГГц) | Разделяется на: LLM-префилл/декодинг + **OCR (Tesseract, многопоточный)** + сервисы |
| RAM | 64 ГБ DDR4 ECC | page cache, OCR-буферы, Kafka/PostgreSQL |
| GPU | **NVIDIA RTX 4090 24 ГБ** (базовая), допустимо A10 24 ГБ | LLM Qwen3-14B-Q4 (KV 32k ≈ 14–17 ГБ VRAM) |
| SSD | NVMe 512 ГБ | Система, PostgreSQL, веса LLM |
| HDD | 2 ТБ SATA RAID1 | Документы/архив/бэкапы |
| Сеть | ≥1×10 Гбит/с, доступ к nvd.nist.gov + bdu.fstec.ru | Security Posture Analyzer (ТЗ 2.4) |
| БП | ≥850 Вт | TDP RTX 4090 ≈ 450 Вт |

### 3.2 CPU для OCR (Tesseract)
- Tesseract OCR выполняется на **CPU** (многопоточный, `TESSERACT_OCR_THREADS=8` на 16+ ядрах).
- Требование: извлечение текста ≤2с (без OCR, ТЗ 4.1); OCR-страницы — асинхронно, не блокируют KPI 500+/час.
- При недоборе скорости OCR (сканированные PDF пакетами) — вертикальное масштабирование CPU (до 24 ядер) без смены GPU.

### 3.3 VRAM-баланс LLM (Qwen3-14B-Q4, контекст 32k)
| Статья | Объём |
|---|---|
| Веса (Q4_K_M, 14B) | ~9–10 ГБ |
| KV-кэш 32k токенов | ~2.3 ГБ |
| Оверхед/батч | ~2–4 ГБ |
| **Итого** | **~14–17 ГБ** → укладывается в 24 ГБ ✅ |

27B (IQ3/Q4) на 24 ГБ **не помещается** (веса Q4 ~16–17 ГБ + KV ~8 ГБ ≈ 25 ГБ) и **не тянет KPI**
(~200–300 док/час). Резерв для 27B — GPU 48 ГБ (L40S / 2×A10).

### 3.4 KPI-обоснование
- 500+ док/час ≈ ~1450 tok/s агрегатно → достигается **чанкингом контекста ≤4k + continuous batching (vLLM) + regex-first** для сетевых индикаторов.
- Latency LLM ≤5с (KPI) — типовое письмо ≤10k токенов за 1–2 батча.
- DOCX ≤3с, извлечение ≤2с, проверка уязвимости ≤15с (с кэшем Redis) — софтовые ограничения, железо покрывает.

## 4. Формат JSON-схемы для обмена с внешними API

Полные схемы — `phase1_json_schemas.md` (NVD API v2, BDU ФСТЭК, CMDB, нормализованная схема уязвимости).

Краткое резюме (нормализованная уязвимость, источник `nvd`/`bdu`/`manual`):
```jsonc
{
  "source": "nvd",
  "cve_id": "CVE-2026-1234",
  "bdu_id": null,
  "severity": "critical",
  "cvss": {"score": 9.8, "version": "3.1", "vector": "CVSS:3.1/..."},
  "affected_range": {"version_end_including": "1.1.1k"},
  "fixed_version": "1.1.2",
  "patch_url": "https://www.openssl.org/news/security.html",
  "cmdb": {"match": true, "installed": {"product": "OpenSSL", "version": "1.1.1k", "host": "srv-mail"}},
  "recommendation": "Обновить OpenSSL с 1.1.1k до 1.1.2"
}
```
