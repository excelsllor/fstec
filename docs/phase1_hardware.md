# Приложение 8: Требования к аппаратному обеспечению

ТЗ: п. 8 «Требования к аппаратному обеспечению (GPU для LLM, CPU для OCR)».

---

## 1. Целевая модель LLM
- **Qwen3-14B-Instruct**, квант **Q4** (GGUF) через **vLLM** (OpenAI-совместимый API, абстрактный LLMProvider).
- Отринутый вариант: Qwen3.8-27B в IQ3/Q4 — **не помещается на 24 ГБ** (веса Q4 ~16–17 ГБ + KV-кэш 32k ~8 ГБ ≈ 25 ГБ) и **не тянет KPI** (decode ~55–80 t/s, 10–15с/письмо, ~200–300/час). 27B возможен только на 48 ГБ (L40S/2×A10).
- Резерв качества NER организаций/сроков/контактов: LoRA-финтюн 14B по данным пилота (не блокирует MVP), либо regex-first для сетевых индикаторов (Индикаторы точны независимо от модели).

## 1.1 OCR и быстрая классификация (Фаза 2.5)
- **PaddleOCR** (GPU, CUDA) — основной OCR-движок для русского скана (det + rec + cls, `lang="ru"`), `FSTEC_OCR_ENGINE=auto|paddle|tesseract`. **Tesseract** — CPU fallback.
- PDF → изображения: `pdf2image`/`poppler`; распознавание выполняется на GPU ingest-сервиса (4090), итог ≤2с/страницу; KPI 500+/час достигается параллельным распознаванием страниц.
- **RuBERT** (`DeepPavlov/rubert-base-cased-conversational`; прежний id `sberbank-ai/…` отвечает 404 на HuggingFace) — быстрый детерминированный классификатор категорий (hacker|compromise|vulnerability|other), работает на **CPU** (GPU целиком под vLLM); классификация через cosine-к-NN по фразам-сеедам → label+confidence; при низкой уверенности → heuristic-fallback → Qwen-валидация.
- Баланс памяти GPU: 4090 (24 ГБ) — vLLM (Qwen3-14B-Q4 ≈ 16–17 ГБ + KV), без конфликта с RuBERT (CPU).

## 2. KPI-обоснование железа
- Требования времени: LLM ≤5с (4.1), генерация DOCX ≤3с (4.1), извлечение текста ≤2с (4.1), проверка уязвимости ≤15с (1.4), пропускная **500+ документов/час** (4.1).
- 500/час ≈ **~1450 токенов/с** агрегатно (средний документ ~10k токенов вход + 500 выход).
- Достижение на 14B-Q4: **чанкинг контекста ≤4k токенов + continuous batching (vLLM) + regex-first** для индикаторов (LLM не «жуёт» весь документ на индикаторах).

## 3. Рекомендуемая конфигурация сервера

| Компонент | Спецификация |
|---|---|
| **ОС** | RED OS 8.x (amd64); Docker + docker-compose; CUDA 12.x + NVIDIA driver |
| **CPU** | 16–24 ядра / 16–32 потока (Xeon Silver 4309Y / EPYC 7262 и выше) |
| **RAM** | 64 ГБ DDR4 ECC |
| **GPU (LLM)** | **NVIDIA RTX 4090 24 ГБ** (базовая); допустимо **A10 24 ГБ** при чанкинге. (27B — только 48 ГБ: L40S / 2×A10) |
| **SSD (система+БД+веса)** | NVMe 512 ГБ |
| **HDD (документы/архив)** | 2 ТБ SATA RAID1 (бэкапы/архив) |
| **Сеть** | ≥1× 10 Гбит/с (доступ к BDU/NVD) |
| **БП** | от 850 Вт (под RTX 4090, TDP ~450 Вт) |

Примечание: SSD-кэш bcache **не требуется** — page cache (64 ГБ RAM) покрывает «горячие» документы.

## 4. Расчёт VRAM (14B-Q4, контекст 32k)
| Статья | Объём |
|---|---|
| Веса 14B (Q4_K_M) | ~9–10 ГБ |
| KV-кэш на 32k токенов (~72 КБ/токен) | ~2.3 ГБ |
| Оверхед/батч | ~2–4 ГБ |
| **Итого** | **~14–17 ГБ** → помещается в 24 ГБ ✅ |

## 5. Ожидаемая производительность (одна RTX 4090, 14B-Q4, vLLM)
| Метрика | Ожидание |
|---|---|
| Latency LLM (типовое письмо ≤10k токенов, чанки ≤4k) | ~2–4 с ✅ (KPI ≤5с) |
| Пропускная способность | ~1000–1500 док/час ✅ (KPI 500+/час) |
| DOCX-отчёт | ≤3 с ✅ |
| Проверка уязвимости (NVD/BDU + CMDB) | ≤15 с ✅ (с кэшем Redis) |

Резерв: при недоборе KPI на больших письмах → 2-я GPU (2×A10/4090) или снижение максимального контекста.

## 6. Требования к окружению
- Обязательный доступ в интернет к **bdu.fstec.ru** и **nvd.nist.gov** (по решению Заказчика) — необходимо для Security Posture Analyzer (ТЗ 2.4).
- CMDB Заказчика — через API (ТЗ 4.3); в dev используется CMDB-mock.
- Защищённый канал для доступа Исполнителя (ТЗ 3.2): VPN/по согласованию.

## 7. Развёртывание (продуктивный контур)
- **Docker Compose** (все сервисы): api-gateway, ingest, llm (vLLM), security, reporting, kafka, redis, postgres, nginx, cmdb-mock (dev-only).
- Python-зависимости и образы — статически зафиксированы (пиннинг версий); сборка для RED OS.
- Мониторинг: healthcheck каждого сервиса, логи в journald/EFK, метрики DOCX/LLM-латентности.
- Бэкапы: PostgreSQL (pg_dump nightly) + файлов (uploads/reports) на HDD-архив; RTO ≤30 мин (ТЗ 4.2).
