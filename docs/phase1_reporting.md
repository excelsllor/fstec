# Структура DOCX-отчётов (ТЗ 2.5.1) и категории документов (ТЗ 8)

---

## 1. Карточка индикаторов — структура

Именование файла: **`Report_[Исходное_имя]_[YYYY-MM-DD].docx`** (ТЗ 2.5.1).
Пример: `Report_9-104.pdf_2026-09-07.docx`

Общие параметры документа:
- Шрифт: Times New Roman 14pt, межстрочный интервал 1.15, поля 3/1.5/2/2 см (ГОСТ Р 7.0.97-2016).
- Цветовая индикация рисков (ТЗ 4.4): **Красный** — критическая угроза/уязвимость,
  **Жёлтый** — средняя опасность, **Зелёный** — угроз не выявлено.

### 1.1 Шапка (ТЗ 2.5.1)
```
[Название организации Заказчика (реквизиты)]

Дата: YYYY-MM-DD
Исходный файл: <Исходное_имя>            (например 9-104.pdf)
ID заявки: <document_id>
```

### 1.2 Раздел 1. Список IP-адресов
- **Группировка IPv4 / IPv6**, без дубликатов.
```
1. Список IP-адресов
   IPv4:
   - 1.2.3.4
   - 192.168.0.0/24
   IPv6:
   - 2001:db8::1
```
- CIDR-нотация поддерживается (ТЗ 2.3.2).

### 1.3 Раздел 2. Список доменных имен
- **С указанием корневого домена** (публичный суффикс).
```
2. Список доменных имен
   - evil.example.com         (корневой домен: example.com)
   - example.com              (корневой домен: example.com)
```

### 1.4 Раздел 3. Список Email-адресов
```
3. Список Email-адресов
   - boss@example.com
   - tag+plus@example.com
```

### 1.5 Раздел 4. Результаты анализа уязвимостей
Таблица: **CVE ID | CVSS Score | Затронутое ПО | Текущая версия | Целевая версия | Статус угрозы**

| CVE ID        | CVSS | Затронутое ПО | Текущая версия | Целевая версия | Статус угрозы |
|---------------|------|---------------|----------------|----------------|---------------|
| CVE-2026-1234 | 9.8  | OpenSSL       | 1.1.1k         | 1.1.2          | **Красный (Critical)** |
| CVE-2026-5678 | 5.4  | nginx         | 1.22           | 1.24           | Жёлтый (Medium) |
| —             | —    | —             | —              | —              | Зелёный (нет угроз) |

- Статус угрозы определяется заливкой ячейки: красный/жёлтый/зелёный.
- При отсутствии уязвимостей — «Уязвимости не обнаружены» (зелёный статус).

## 2. Проект ответа (ТЗ 2.5.2)

### 2.1 Если угроза обнаружена
- Содержит **требование/рекомендацию срочного обновления** ПО.
- **Без раскрытия внутренней архитектуры Заказчика** (без имён хостов/внутренних сервисов).
- Приводится рекомендация «Обновить {Product} с {current_ver} до {fixed_ver}» (ТЗ 2.4).

### 2.2 Если угроза не обнаружена
- Уведомление о том, что используемое ПО **не подвержено риску**.

### 2.3 Структура проекта ответа
```
[Centered bold] Ответ на письмо {номер} от {дата}

Сообщаем о принятых мерах ...

1. <тип угрозы>
   - мера 1;
   - мера 2.

[Подпись должностного лица: должность, ФИО (настраивается в конфигурации)]
```

## 3. Категории документов (ТЗ 8 «Перечень категорий документов и примеры»)

| Категория | Ключ | Описание | Пример |
|---|---|---|---|
| Информационное письмо | `info` | Уведомление без угроз | «Письмо о порядке взаимодействия» |
| Хакерская группировка | `hacker_group` | Данные о деятельности хакерских группировок, IOC | Письмо с IP/доменами/email злоумышленников |
| Уязвимости ПО | `vulnerability` | Информация об уязвимостях (CVE/BDU, версии ПО) | «Об уязвимости OpenSSL 1.1.1k» |
| Компрометация | `compromise` | Сведения о компрометации/инциденте | «О компрометации учётных данных» |
| Прочее | `other` | Не относится к вышеуказанным | Разное |

> Источник категорий: классификатор монолита (`letter_analyzer`) — расширяется ключами под LLM-классификацию (ТЗ 2.3.1 «и др.»).
