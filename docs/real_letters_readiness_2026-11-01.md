# Поведение на реальных письмах — оценка перед capacity-тестом

## Что будет делать программа

1. Принять PDF/DOCX/RTF/ODT/XLSX/TXT через веб-интерфейс или API.
2. Извлечь текст, таблицы и при наличии — OCR для сканов.
3. Определить тип письма: фишинг/хакерская группировка или уязвимости BDU.
4. Извлечь BDU/CVE, описание, CVSS, уровень опасности, затронутое ПО.
5. Сверить ПО со списком GLPI и определить применимость/действие.
6. Сформировать меры и ответ, затем отчёт DOCX.
7. Вернуть документ в очередь; обработка асинхронная, статус виден в UI.

## Что уже подтверждено на 22 уникальных письмах

- **BDU-покрытие**: 222/222 эталонных BDU найдены, recall 100%.
- **BDU precision**: 99.11%; два лишних BDU в ответах (`BDU:2023-01528`, `BDU:2026-10095`).
- **Применимость**: 98.98% совпадений по классу действия; но есть 2 решения `not_used`, расходящиеся с эталоном.
- **Меры**: все эталонные меры найдены (recall 100%), но precision 95.62%; есть лишние/расширенные меры, особенно в `9/85`.
- **CVSS**: только 56.76% верных версий методики; основная систематическая ошибка — `2.0/3.0/4.0` вместо `3.1`.
- **Уровень опасности**: 94.12%; 13 расхождений, в основном завышение до «критический».
- **Структура**: ответы близки к эталонам по тексту (char ~97.9%), но это не полевая корректность.

## Как программа, вероятнее всего, справится с реальным потоком

### Сильные стороны

- Стандартные письма ФСТЭК с BDU-карточками и перечнем мер разбираются структурно хорошо.
- Все BDU из эталонов были найдены; ответы сохраняют заголовок, вступление и порядок уязвимостей.
- Применимость по списку GLPI в основном совпадает с эталонными решениями.
- Асинхронная обработка не теряет загруженные документы: при нагрузке растёт очередь и latency, но не происходит синхронного таймаута UI.
- Есть статусы, повторная обработка и ручное заполнение полей; это позволяет использовать ответ как черновик.

### Риски на реальных письмах

1. **CVSS-версия будет ошибаться системно**, если не исправить источник версии. Для реальных BDU-писем это не косметика, а неверное поле.
2. **Уровень опасности может завышаться**; 13/221 ошибок на выборке — существенно для приёмки.
3. **Лишние BDU** опаснее пропущенных: оператор может проверять несуществующую уязвимость. Нужна сверка каждого BDU с источником.
4. **Решения `not_used` зависят от полноты GLPI**. Программа проверяет только список ПО, а не фактическую установку; при неполном списке она уверенно напишет «не используется». Это ограничение надо явно показывать оператору.
5. **Состав мер**: модель может добавлять меры, повторять их и менять падежи. Для реального письма нужен редактор/проверка состава мер.
6. **Сканы и нестандартные вложения**: OCR и таблицы могут дать пропуски BDU/версий. На 22 PDF без сложного OCR это не проверено в достаточной мере.
7. **Смешанные письма**: несколько BDU в одном абзаце, вложенные таблицы, несколько писем в одном PDF — парсер может объединить или потерять запись.
8. **LLM-вариативность**: одинаковые входы сейчас дают одинаковый результат на копиях, но реальные тексты будут отличаться; нужна проверка на новых уникальных письмах, а не только на копиях.

## Ожидаемое качество по типам писем

| Тип письма | Ожидание |
|---|---|
| Типовое BDU-письмо с готовым перечнем уязвимостей | Хорошая структура и BDU-покрытие; **обязательная проверка CVSS/severity** |
| Фишинговое письмо с группировкой и перечнем мер | Хорошее покрытие мер; возможны лишние меры и повторы |
| Скан/фото/плохой OCR | Средний риск пропусков; нужен контроль текста и BDU |
| Смешанное письмо с таблицами/вложениями | Повышенный риск; нужна ручная сверка |
| Письмо без BDU/с неполными данными | Возможны пропуски полей; ответ только как черновик |

## Правильный порядок работы для демонстрации

1. Загрузить 1–2 эталонных письма, не 100 копий.
2. Проверить поля: BDU, CVSS-версию, severity, применимость, состав мер.
3. Показать, что при неполном GLPI система говорит «не используется» как **предположение по списку**, а не как факт установки.
4. Не заявлять 97.9% как семантическую точность; показывать полевые метрики.
5. Под нагрузкой показывать очередь и статусы, а не обещать мгновенную обработку.

## Вывод

Программа пригодна как **ассистент для подготовки черновика ответа** на типовые письма, но не для автоматической отправки без проверки. Главный блокер — CVSS-версия; второй — severity, лишние BDU и лишние меры. После исправления CVSS и добавления полевых проверок риск снижается, но решения по применимости всё равно требуют контроля полноты GLPI.
