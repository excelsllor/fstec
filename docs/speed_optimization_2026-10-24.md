# Анализ скорости и варианты ускорения — 2026-10-24

## 1. Куда уходит время

### Hacker-письмо (после оптимизаций)

| Этап | Время | Доля |
|---|---:|---:|
| upload + parse | ~2–3 с | ~7% |
| LLM analyze+extract (merged) | ~20–30 с | ~60% |
| security / BDU / CMDB | ~2–5 с | ~10% |
| reporting, reference без `plan_reply` | <1 с | ~2% |
| Kafka/DB/очередь/поллинг | ~5–10 с | ~15–20% |
| **Итого p50** | **36.6 с** | 100% |

### Vulnerability-письмо

| Этап | Время | Доля |
|---|---:|---:|
| upload + parse | ~2–3 с | ~2% |
| LLM analyze + extract (раздельно) | ~30–60 с | ~30% |
| security: 24–40 BDU/NVD + CMDB | ~20–60 с | ~25–35% |
| reporting: `plan_reply` | ~20–40 с | ~25% |
| Kafka/DB/очередь | ~5–15 с | ~10% |
| **Итого** | **~100–180 с** | 100% |

Главный ресурс — **vLLM-инференс и очередь**. На 8 параллельных запросах T4 обслуживает
запросы пачками; в часовом тесте это дало p50 359 с и 74.5 док/ч. Второй по значимости
фактор для vulnerability — BDU/NVD (до 40 последовательных ID на письмо) и второй LLM-вызов
`plan_reply`.

## 2. Проверенные варианты

| Вариант | Результат | Качество |
|---|---|---|
| SHA-256 dedupe исходника | повторная загрузка **36–53 мс**, `completed` без LLM/BDU | идентичное, тот же документ |
| Reference вместо `plan_reply` для hacker | p50 **87.8 с**, 94.3 док/ч | A/B 22 док.: mean **0.9969**, min **0.9609**, hacker 11/11 = **1.0** |
| merged analyze+extract (не-vulnerability) | p50 **36.6 с**, max 44.7 с, **239.7 док/ч** | threats/iocs совпали; у 9-85 удалён отсутствующий в тексте `telegram.org` |
| `plan_reply max_tokens=2500` | без ошибок схемы; ограничивает хвост | не меняет валидные ответы |
| Reference для vulnerability | **не включён**: A/B min 0.9609 без полного эталона | риск изменения формулировок |

Итог по сравнению с исходным часовым тестом: p50 359 с → **36.6 с** на hacker-письмах
(окно 3 параллельных), throughput в коротком окне 74.5 → **239.7 док/ч**. Это не подтверждает
500+/ч на длительном прогоне, но показывает запас после устранения лишних вызовов.

## 3. Что делать дальше (в порядке риска)

1. **Поднять параллелизм и батчинг**: `max-num-seqs`, `FSTEC_LLM_CONCURRENCY`, батчинг
   Kafka; проверить 8–16 одновременных писем. Ожидаемо линейный рост до насыщения T4.
2. **Один chunk вместо двух** для писем 8–12k токенов: сейчас 9-89 делает 2 merged-вызова
   (7130 + 1742 токена). Нужен A/B по threats/iocs/метрикам.
3. **Vulnerability reference**: собрать эталоны и проверить отказ от `plan_reply`;
   потенциально −20–40 с на письмо.
4. **BDU/NVD prefetch**: извлекать ID заранее и прогревать кэш; ограничить retry для
   недоступных ID.
5. **GPU**: T4 → A10/A100 или Qwen-3B/AWQ при сохранении качества; это единственный путь
   к устойчивым 500+/ч.

## 4. Ограничения

- Быстрые замеры 3–8 документов не заменяют часовой KPI.
- Dedupe срабатывает после завершения первого документа; два одновременных одинаковых
  upload до завершения обработаются отдельно.
- После последнего теста сервер перестал отвечать по SSH/HTTPS; результаты зафиксированы
  до потери связи, состояние контейнеров нужно проверить через консоль/сеть.
